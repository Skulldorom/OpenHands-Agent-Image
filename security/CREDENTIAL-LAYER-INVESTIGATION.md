## Detector correction

`tests/test-image-layers.py` uses named rules. PEM detection requires evidence of encoded key material after a header: at least 16 Base64 characters, including whitespace-wrapped forms, or the legacy encrypted-key `Proc-Type` header. JSON/JavaScript escaped CR/LF separators are normalized before detection. The deliberately low threshold blocks truncated keys without requiring a footer or successfully parseable DER. GitHub token and AWS access-key rules remain unchanged and are evaluated independently after harmless format literals. No file path or binary-file exemption is added. Existing credential-file and historical-layer/whiteout checks remain active.

The scanner still operates directly on bytes, including NUL-containing and invalid-UTF-8 files. It does not decode with ignored errors or discard binary files. Error messages contain rule/location only, never matched values or surrounding bytes. Original file-size/directory scope is unchanged; this is a targeted fix, not a claim that all possible credential encodings are detected.

Regression tests use synthetic binary format literals and synthetic credential examples: all five GitHub short-token prefixes, fine-grained PATs, AWS access keys, untyped/RSA/EC/OpenSSH/encrypted PEM boundaries with payload, CRLF and escaped separators, unusually short wrapped lines, legacy encrypted headers, truncated keys, and a real token pattern after a harmless marker. Nested-archive tests continue to block credentials recoverable beneath a later whiteout. Assertion messages are checked for absence of matched values.

Final validation scans both the pinned upstream image's saved layers and every saved candidate layer, in addition to Git identity, PostgreSQL initialization/query/backup/restore and Agent Server readiness/API/signal Docker integration. See the PR's final validation run for the result; the investigation runs intentionally retained the failing detector while gathering evidence.

## Full-file streaming scan and AWS substring classification — 2026-11-17

The full-PR audit removed the old small-file/selected-directory pattern-scan limits. Every regular file is now streamed in bounded chunks across every saved layer, including large binaries and deleted historical files. Root credential-file names are preserved during path normalization; nonempty credential files cannot hide after a long whitespace prefix. Real PEM material, GitHub tokens/PATs and standalone AWS access-key IDs remain blocking. Chunk boundaries and arbitrarily padded/wrapped partial PEM payloads are tested.

Expanding coverage identified an AWS-shaped substring in official upstream layer `sha256:1971d2a873adc60b815a2afec78d6befc3ce15025264c1a08ecec191e80a5688`, file `openhands/.code-server/lib/node`. [Hash-only diagnostic run](https://github.com/Skulldorom/OpenHands-Agent-Image/actions/runs/44112846768) records a 20-byte match with SHA-256 `b815da9bd749f313471ad91a3d3408d8f096da9788dfd9ae0893fb8b6ed232ce`, with alphanumeric bytes both before and after it. Its data section has flags 2, not executable flags. The finding does not match the standard AWS documentation example; no matched bytes or context were logged.

Classification: the old unbounded regular expression matched an arbitrary 20-character slice inside a longer alphanumeric data sequence, rather than a standalone AWS access-key identifier. AWS documents an access-key ID as a 20-character identifier ([official example and format](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/MakingRequests.html)). The rule now requires alphanumeric token boundaries. This is a lexical correction, not a Node/binary/directory/hash exclusion, and not an exemption for executable sections. Classified substring matches are reported by rule and hash. Standalone IDs, including valid IDs embedded in executable-section test fixtures, still block. Tests also check that classifications never print the matched value.

Hash-only diagnostics in [run 44115265186](https://github.com/Skulldorom/OpenHands-Agent-Image/actions/runs/44115265186) found no public-placeholder markers. We do not assert it is a fake token, and never used it for authentication or printed/copied its value.

Provenance/age proof: authenticated [integration job 134087417504](https://github.com/Skulldorom/OpenHands-Agent-Image/actions/runs/44097217505/job/134087417504), at source `f6cd8621346e2ef2b61b1c543748a525fd75c026`, successfully pulled exact official upstream `sha256:6a0fe47417e1d1227592f693880b0292ebdd4f59fbfe517c8b8685e7c455abe3`. At **2026-11-17 13:54:23.999522 UTC** it recorded the upstream RootFS diff-ID list including this exact immutable layer. The present bytes therefore existed no later than 13:54:24 UTC; this is not an untrusted file/build timestamp assumption.

[GitHub documents installation-token expiration after one hour](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app). If authentic, this installation-token-shaped literal could not remain live beyond 14:54:24 UTC. The classification becomes effective only after that bound. Authenticity is unknown; the decision is **known non-live installation-token-shaped literal**, not a claim of a public test placeholder. The literal remains upstream and visible as a classified finding.

The scanner recognizes only this exact SHA-256 plus the `ghs_` legacy installation-token family and the proven age bound. It records the classification explicitly, then continues scanning every remaining byte/match in the same file/layer. No binary, directory or entire layer is excluded. Changed fingerprints, other token families, current stateless `ghs_APPID_JWT` tokens and any other credential material remain blocking. Time-bound/exact-match tests and same-file additional-secret tests enforce this. A sealed `layer-classifications.json` reports the exact candidate, inspected layer count, classified fingerprints and zero unclassified detections; the publisher verifies the classifications again.
